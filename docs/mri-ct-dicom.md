# DICOM для МРТ и КТ

Маршруты `POST /api/v1/mri` и `POST /api/v1/kt` принимают один DICOM с `Content-Type: application/dicom`. Для имён `.dcm` и `.dicom` также допускаются пустой Content-Type и `application/octet-stream`. Прежние TIFF для МРТ и MP4 для КТ остаются допустимыми.

Конвертация выполняется в `exam_service` после события загрузки и до существующего события для МЛ. МРТ преобразуется в многостраничный одноканальный 16-битный TIFF и далее разбивается на PNG прежним кодом. КТ преобразуется в MPEG-4/MP4, 15 кадров/с. Порядок кадров внутри DICOM сохраняется. Нечётные размеры видео дополняются до чётных чёрным краем.

В прежний ключ S3 `<id>/<id>` записывается TIFF или MP4 с соответствующим Content-Type. Для МРТ используется bucket `mri`, для КТ — `kt-b`, как в существующем МЛ-сервисе. Исходный DICOM сохраняется побайтно в `<id>/original.dcm` того же bucket. События `mrisplitted` и `ktprepared` и их поля не меняются. При ошибке конвертации или сохранения событие для МЛ не публикуется; обработчик загрузки возвращает ошибку существующему consumer.

## Запуск

Для сборки `exam` нужен Go 1.25 или новее, как для DICOM-декодера УЗИ. Для КТ необходим `ffmpeg` в PATH; он устанавливается обновлённым `exam/Dockerfile`.

Пересобрать и перезапустить backend из корня `med_ml`:

```sh
docker compose --profile app up -d --build --no-deps composition_api exam_service ml_exam_service
```

Состояние развёртывания и сквозной проверки описывается в отдельном отчёте.

## Проверка

В каталогах `exam` и `composition-api` выполнить:

```sh
go test -mod=readonly ./internal/... ./cmd/...
```

В `exam` FFmpeg должен быть в PATH, иначе тест чтения MP4 будет пропущен. `DICOM_TEST_DIR` позволяет дополнительно проверить TIFF-конвертацию реальных `.dcm` из указанной папки.

Автоматические проверки охватывают однокадровые и многокадровые изображения, signed и 12-битные grayscale, MONOCHROME1, RGB/YBR, JPEG Baseline и RLE, сохранение оригинала, ошибки хранения, прежние форматы API, число и порядок кадров MP4. Сквозная обработка реальных МРТ/КТ моделями требует отдельных образцов и запущенных сервисов.

## Ограничения

Поддерживается один DICOM, включая обычный многокадровый; серия отдельных файлов или ZIP не собирается в исследование. Modality не ограничивается тегом MR/CT: маршрут определяет целевой формат.

Для grayscale применяются RescaleSlope/RescaleIntercept и первое LINEAR-окно WindowCenter/WindowWidth. При отсутствии окна используется диапазон BitsStored. Для МРТ результат нормализуется в 16-битный диапазон: существующая модель принимает один канал и делит значения на 255×255. Для КТ используются 8-битные значения; это не сохраняет исходные HU. MP4 использует сжатие с потерями.

КТ-модель требует минимум 54 кадра: DICOM с меньшим числом кадров отклоняется до публикации события МЛ. Кадры не дублируются искусственно. Для однокадрового КТ потребуется загрузка серии, которая пока не реализована.

При сквозной проверке также исправлены существующие ошибки КТ: чтение JSONB-предсказаний, переход статуса к `completed`, заглушка GET, отсутствие вероятностей в HTTP-ответе и лишняя размерность grayscale-тензора классификатора. Номера полей ML-события `KtProcessed` приведены к существующему контракту backend (100/200). Веса моделей и входные события ML не изменены.

LUT-последовательности, Enhanced DICOM с Shared/Per-frame Functional Groups, неподдерживаемые фотометрические представления и кодеки отклоняются. Ограничения входа: 512 MiB и 64 миллиона декодированных samples; например, до 256 grayscale-кадров 512×512. FFmpeg ограничен двумя минутами и контекстом обработки.

Для конкретного аппарата и модели необходимо проверить окно яркости и результат на реальных МРТ/КТ. Доступные в рабочей папке реальные УЗИ-DICOM проверяют декодирование, но не качество моделей МРТ/КТ.
